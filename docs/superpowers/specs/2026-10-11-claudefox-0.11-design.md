## A. Page safety

**A1 · Site list per chat**
- A site is the URL's lowercase host without a leading `www.`. A list entry matches its own host and every subdomain (`youtube.com` matches `m.youtube.com`). IP addresses and `localhost` match exactly. file: pages follow the local-page grants, not the list.
- Each chat's list starts from:
  - the chat window's active tab when a message is sent;
  - every http(s) URL in the message, plus every bare domain ending in com, net, org, edu, gov, io, dev, app, ai, co, me, tv, info, br, pt, uk, us, de, fr, es or it;
  - @tabs (E9) and the context-menu page or link (E1);
  - sites marked Allow in the site list (A7).
  Entries added with "Allow this chat" last for the chat. "Allow this message" entries end with the message.
- Checked: every tool that reads or acts on a tab, and the targets of navigate and tab_open. Not checked: tabs_list (A4 filters it instead), progress, the army tools, watch_video (it has its own card), file tools and the output tools.
- A call outside the list shows a card in that window's panel: "Claude wants to use `<site>`", the action (read the page, act on the page, open the page), and three buttons: Allow this message, Allow this chat, Deny.
  - One card at a time per window; calls for the same site wait on the same card.
  - No answer in 120 s, or no panel open within 5 s, counts as Deny.
  - After a Deny, further calls to that site in the same message are refused without a card.
- A refused call returns: `The user did not allow <site>. Do not try it again in this message.`
- Checked tools get `timeoutMs: 150000` so a card has time.

**A2 · Asking after a page read**
- A message becomes "page-read" once any PAGE_CONTENT tool has returned in it.
- In a page-read message, each of these asks first (one card each, Allow or Deny, same timeouts):
  - a click, Enter, or submitting type_text whose target submits a POST form (form method or formmethod post);
  - a click on a link to another site;
  - navigate to a site other than the tab's current one;
  - tab_open to a site other than the chat window's active tab.
  GET forms inside the list do not ask.
- A new page-side operation classifies the target before acting and returns `{ submitsPost: boolean, leavesTo: site | null }`.
- A script-driven POST without a form cannot be seen. The prompt and the docs say so.

**A3 · WebFetch inside the list only**
- The chat settings file gets a PreToolUse hook for WebFetch that runs `node host/webfetch-hook.js`.
  - The script reads the hook JSON from stdin and asks the helper over its pipe (with the pipe token) `{type:'webfetch_check', session, url}`.
  - It exits 0 to allow, or 2 with the reason on stderr to block. If the helper can't be reached, it blocks.
- The helper allows a fetch only when both hold:
  - the message has not read a local file or local page;
  - the URL's site is in that chat's list, or Trusted mode is on.
- The add-on sends `{type:'scope', chat, sites, trusted}` with every message and whenever the list changes. The helper learns about local reads two ways: from the stream (Read, Glob, Grep, read_document), and from the add-on's `{type:'local_read', chat}` for file: pages.
- WebSearch stays allowed.
- Fallback, if hooks don't run under `claude -p --settings` on F's CLI (live check 3): WebFetch leaves `--tools`, and a Settings switch "Web reading" (off by default) brings it back.

**A4 · tabs_list**
- It lists only the chat window's tabs.
- Tabs outside the list return `{id, site, active}` and nothing more. In Trusted mode, every tab returns its title and URL.

**A5 · Trusted mode**
- A switch in Profile → Permissions under Unsafe mode, with the note "Claude acts on any site without asking. Pages can try to steer it."
- Off by default and for the session only: Stop and a helper restart turn it off. Turning it on needs the confirm window (kind `trusted`).
- It lifts A1, A2, A3's site rule and A4's redaction. It does not lift:
  - a Block in the site list (A7);
  - A3's local-read rule;
  - the blocks that only Unsafe lifts (Google sign-in, password pages);
  - the upload card (E13).

**A6 · Prompt**
- The chat prompt's line "Otherwise there is no confirmation step" becomes: "Some actions ask the user first in a card in the chat: using a site outside this chat's sites, submitting a form or leaving a site after reading a page, and uploads. You cannot answer the card. If a tool says the user did not allow something, stop that path and say so in one line."
- With Trusted on, it reads: "Trusted mode is on: act directly; there is no confirmation step."
- The tool server's instructions say the same.

**A7 · Site list**
- Profile → Permissions → Sites shows one row per site, each with Allow or Block and a remove button, plus an "Add site" field.
- Saved in storage.local `sites` as `{ "<site>": "allow" | "block" }`. Sites not listed are Ask.
- Block refuses every tool on that site, and navigate or tab_open to it, in every mode, with: `<site> is blocked in your site list.` tabs_list shows blocked sites as id and site only.

**A8 · Workers**
- army_start copies the lead's list (A1 plus A7's Allow entries) into the run. Workers never show cards.
- A worker call outside the list is refused with: `Outside the sites the lead may use: <site>.`
- A2 actions are refused for workers with: `Workers cannot submit forms or leave the site; report back to the lead.`

**A9 · network_log**
- It goes through the same page gate as console_log, plus A1.

**A10 · Sensitive fields beyond English**
- Add these to the password, two-step and payment patterns:
  - password: senha, contraseña, clave;
  - two-step: código de verificação, código de segurança, verificação em duas etapas, código de acceso, código de verificación;
  - payment: cartão, número do cartão, nome no cartão, validade do cartão, vencimento, CVV, CVC, tarjeta, número de tarjeta, fecha de vencimiento, titular.
- One check per term.

## B. Files, local pages and the helper

**B1 · Broad folders**
- File tools and local pages refuse:
  - a drive root;
  - the home folder;
  - %APPDATA% and %LOCALAPPDATA%;
  - any folder that contains the data folder.
  The error: `<folder> is too broad for Claude: pick a folder inside it.`
- Edit and Write denies are added beside every Read deny, and also cover:
  - the whole data folder;
  - the Startup folder (`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`);
  - the WindowsPowerShell and PowerShell profile folders under the real Documents folder. That folder is read from the User Shell Folders registry value `Personal`, falling back to `%USERPROFILE%\Documents`.
- Chat, worker and Improve turns pass `--setting-sources user`.
- The file-tools confirm says: "Claude can read [and write] files in this folder only. It never gets a shell, and it cannot write to startup folders, PowerShell profiles or Claudefox's own files."

**B2 · Secret paths**
- Folders: `%APPDATA%\` discord, discordcanary, discordptb, Slack, Telegram Desktop, GitHub CLI, `Microsoft\Windows\PowerShell\PSReadLine`, `Code\User\globalStorage`, `Cursor\User\globalStorage`, `VSCodium\User\globalStorage`, and `~/.config/gh`.
- Files: `*.key`, `*.ovpn`, `wallet.dat`.

**B3 · Local page grants**
- Grants last for the helper's session. On its first 0.11 start, the helper deletes local-grants.json and logs: `Saved local-page folders were cleared: they now last one session.`
- The local-page confirm adds "Claude was reading: `<site>`": the last page site read in the message, or "no page".

**B4 · Folder picker**
- A folder picked in the Windows picker goes through the file-tools confirm before it replaces the old one. No keeps the old folder.

**B5 · State sync**
- The helper sends `{type:'confirmed_state', unsafe, trusted, files: {mode, folder} | null}` after hello and after every change. The add-on sets its switches from it.

**B6 · Improve**
- Arguments:
  - `--permission-mode dontAsk`;
  - `--tools Read,Glob,Grep,Edit,Write`;
  - `--allowedTools` with Read, Glob, Grep, plus Edit and Write limited to the sandbox's `extension/mods/` (in guard.js's rule path format).
- A proposal is refused if it changed any path outside `extension/mods/`, node_modules included.
- Tests run in a fresh copy of the clean base plus the mod's files. A test timeout uses killTree.
- The friends zip carries test/ and host/test/.

**B7 · Remote tool servers**
- Adding an https (or loopback http) server opens the confirm window (kind `mcp_remote`): "Add the tool server `<name>` at `<url>`? When Claude uses it, what it reads from pages can go to that server." Header values are never shown.

**B8 · Confirm window**
- confirm.ps1 shows the text in a read-only monospace box (Consolas 9) with a scrollbar, at most 260 px tall. Control characters other than line breaks are removed.
- Command servers show the exact argument list, one argument per line.
- When `cmd /c` is used, an argument containing `& | < > ^ %` or a line break is refused before the window opens: `That command has characters cmd would run as another command.`

**B9 · Test hooks**
- The PICK, CLAUDE, ZEN_EXE, PIPE, SCRIPT and CONFIRM overrides are read only when `CLAUDE_IN_ZEN_TEST=1`. Tests set it.
- ARMY_* values are used as `min(default, value)`, so they can only lower a limit.

**B10 · Orphan processes**
- The helper keeps `<data>\children.json` (`{pid, kind, started}`), adding an entry at each spawn and removing it at exit.
- At start, it reads the file. For each pid still running whose image is node.exe, claude.exe or cmd.exe, it kills the tree; then it clears the file.
- On Linux, children spawn detached and are killed by process group.

**B11 · Message size**
- An input over 64 MiB is read off the pipe and dropped. The add-on gets `{type:'host_error', error:'A message was too large (N MB, limit 64 MB).'}`.
- A reply over 1 MiB becomes `{type:'error', id, error:'The reply was too large to send (N MB).'}`.

**B12 · Output folder**
- Saved files go to `<data>\output`. On first start, the helper moves files from extension/output (except README.txt) there, adding a number on a name clash.
- The panel opens saved files and the folder through the helper.

**B13 · Model allowlist**
- Chats accept only `speed`, `speedplus`, `quality` and `army` as models; anything else gets `speed`. `selfimprove` stays internal to Improve.

**U1 · START HERE**
- The friends START HERE describes only the signed install and automatic updates. The unsigned install, about:debugging and the signatures preference are removed.

## C. Cost and speed

**C1 · Army lead**
- Default `{opus, high}`. The army card gets a "Max effort" switch, saved in storage.local `armyMax`; when on, the lead runs at max. The prompt states the effort in use.

**C2 · army_wait**
- It waits until every worker is done, or 280 s. The default and the cap are both 280, the minimum 5. The tool server's timeout for it is the seconds + 20.
- Chat children get `MCP_TOOL_TIMEOUT=960000`.

**C3 · progress**
- Prompt and tool text: send progress in the same message as the next tool call, every two or three steps, never on its own.

**C4 · Page reads**
- A worker's get_page_text without max_chars defaults to 12,000 characters.
- New optional argument `query`, for every caller:
  - It returns the page's Markdown blocks (paragraphs, list items, table rows) that contain any query word of 3 letters or more, in any case.
  - Each block comes with its nearest heading, in page order, cut at max_chars.
  - If nothing matches: `No part of the page matches "<query>".` plus the first 40 headings.
- Worker prompt: find or analyze_page first, then get_page_text with query; whole pages only when needed.

**C5 · Compact JSON**
- Tool results are `JSON.stringify(x)`, with no indentation.

**C6 · Worker effort**
- Medium.

**C7 · Server instructions**
- With PANEL or ARMY_TOKEN set, the instructions are one line: `Claudefox browser tools. Follow the rules in your system prompt.` Outside clients keep the long text.

**C8 · One claude process per chat**
- One process per chat, spawned with `--input-format stream-json` (and `--resume <session>` when the chat has a session). Each message is written as one JSON user line, and a turn ends at the `result` event.
- It respawns:
  - when the spawn signature changes: model, effort, caveman, Unsafe, Trusted, file-tools mode and folder, MCP config, plugins, account, watch;
  - after Cancel (killTree);
  - after 10 minutes idle.
- The 1-hour cap applies per turn and cancels that turn.
- If the process exits within 5 s of spawning, with an error and no output, the helper falls back to one spawn per message for the rest of its run and retries the message. It logs: `Claude Code does not take stream input; using one process per message.`

**C9 · Plugin scan**
- startChat uses the cached plugin list at once. A stale cache starts a background refresh that applies from the next turn.

**C10 · Reconnect**
- callZen retries once after 300 ms, but only when the connection failed before the request was written.

**C11 · Cost and tokens**
- From the result event: `total_cost_usd`, `usage.input_tokens`, `usage.output_tokens`, `usage.cache_read_input_tokens`.
- The done line: `Done in 12.3 s · 48k in (40k cached) · 1.2k out · ≈ $0.18 at API prices`. Parts with no data are left out.
- army_wait results add the workers' totals. The army card: `Runs today: 2 of 5 recommended · 310k tokens`.

**C12 · Streaming render**
- Messages carry a `rev` number, bumped on every change; renderChat rebuilds a message only when its rev changed.
- While streaming, the reply's Markdown re-renders at most every 150 ms; the final text always renders.
- saveChat waits until streaming pauses for 1 s or ends.

**C13 · Page text cache**
- get_page_text keeps the converted text per document in `window.__cizSt` for 60 s, keyed by URL, format, scope and a cheap DOM signature (element count and text length).

**C14 · Inject once**
- The page operation is installed once per document as `window.__cizOp`, with `window.__cizOpV = <version>`.
- A call first runs a small probe, and sends the full code only when the version is missing or old.

**C15 · Screenshot**
- JPEG at quality 80 and scale 1 by default.
- Optional `scale: 0.5`. The result then says: `This image is at half size: double x and y for click and hover.`

**C16 · Network log**
- The webRequest listeners attach on Start and detach on Stop.

**C17 · Tool results by id**
- The helper's tool and tool_result events carry the tool_use id. The panel matches by id, falling back to the first running step when there is no id.

## E. Features

**E1 · Context menu**
- Uses the `menus` permission. Three items:
  - "Ask Claude about this selection" (selection);
  - "Ask Claude about this page" (page);
  - "Ask Claude about this link" (link).
- A click opens the sidebar and fills that window's input without sending:
  - a selection, quoted (up to 2,000 characters), with its site;
  - a page's title and URL;
  - a link's text and URL.
- The site of the page or link joins the chat's list.

**E2 · History**
- Chats are kept in storage.local, per account:
  - `chats:<accountId>` holds the list of `{id, title, created, updated, sessionId}`;
  - `chat:<id>` holds the messages.
- Up to 300 chats per account; past that the oldest goes, with a note in the log. Uses the `unlimitedStorage` permission.
- A history button in the chat header opens a drawer with:
  - search over titles and message text, in any case;
  - the list by date;
  - open, into this window, after which the next message resumes that chat's Claude session;
  - per chat, Export Markdown and Delete;
  - Clear history, which asks first.
- The Markdown export: `# <title>`, the date, then `**You:**` and `**Claude:**` turns, with tool steps as `- <tool> on <site>`. It is saved with browser.downloads.
- The text "Each account keeps its own chats" becomes true.

**E3 · Usage meter**
- Shows C11's numbers. When the limit message gives a reset time, the limit card says so ("Your limit resets at 15:00."); otherwise it shows the message itself.

**E5 · Auto-update, the GitHub link and the Update button**
- The public repo is `F-F-Bukharin/Claudefox`. F's clone sits in `claude-in-zen\Claudefox`, which the private repo ignores. `tools/release.json` holds `{"repo": "F-F-Bukharin/Claudefox"}`.
- The friends build's manifest gets two links. Both are written before signing, because they are part of the signed package:
  - `homepage_url = https://github.com/F-F-Bukharin/Claudefox`, shown as the add-on's homepage in about:addons;
  - `browser_specific_settings.gecko.update_url = https://github.com/F-F-Bukharin/Claudefox/releases/latest/download/updates.json`.
  F's Zen build has neither.
- `tools/Publish release.bat` runs `tools/publish-release.ps1`, which:
  - finds the signed friends xpi;
  - writes `updates.json`: `{"addons":{"claude-in-zen@f.local":{"updates":[{"version":"<v>","update_link":"https://github.com/<repo>/releases/download/v<v>/<xpi name>"}]}}}`;
  - copies the branded build into the public clone, for F to review and push;
  - runs `gh release create v<v> <xpi> updates.json --repo <repo>`.
  F runs it with his own gh login. Claude never pushes or publishes.
- The friends Update row says updates arrive by themselves (Firefox checks daily; about:addons → Check for Updates does it at once). It warns when the helper is older than the add-on: "Re-run Set up Claudefox.bat to update the helper."
- Friends on 0.10 install 0.11 by hand once; later versions arrive by themselves. The helper is not part of the add-on, so a helper change still needs setup re-run, and the add-on says so.

**E6 · Onboarding**
- Each line of the panel's setup checklist gets its action:
  - open the Claude Code install page;
  - sign in, which runs the sign-in .bat through the confirm window;
  - re-run setup, which shows the steps.
- The sign-in .bat looks in `%USERPROFILE%\.local\bin`, then `where claude.exe`, then `%APPDATA%\npm\claude.cmd`.

**E7 · Macros**
- Settings → Macros, saved in storage.local `macros`. Each macro has:
  - a name (letters, numbers, dashes);
  - its text;
  - optional army tasks, one per line;
  - optional sites and schedule (E8).
- `/name` sends the text. A macro with army tasks sends in Quality with the army on and lists the tasks.

**E8 · Scheduled macros (read only)**
- Uses the `alarms` and `notifications` permissions. A macro can run daily at HH:MM or every N hours (1 to 24), while the browser is open. A scheduled macro must list its sites.
- A run is skipped and logged:
  - while stopped;
  - after a usage limit hit in the last 2 hours;
  - when another answer is running and doesn't finish within 30 minutes (the run waits until then).
- Allowed tools: tabs_list; tab_open and navigate inside its sites; get_page_text, read_page, find, analyze_page, get_selection, screenshot, scroll; WebSearch; WebFetch on its sites.
- Not allowed: clicks, typing, forms, file tools, the army, Unsafe, Trusted. There are no cards; anything outside its sites is refused.
- The result goes to history under "Scheduled", with a notification.

**E9 · @tabs**
- "@" at the start of a word opens a picker of the window's tabs (title and site, filtered as you type). The choice is inserted as `@[<title>](tab:<id>)`.
- On send, the tokens become `[tab <id>: <title> (<site>)]`, and their sites join the list.
- `/research` sends "Read these tabs and compare them" with the mentioned tabs, using the army when Quality has it on.

**E10 · Reading chips**
- On web pages the starter chips are: Summarize this page, Key points, Translate to Portuguese (Brazil), /tabs, /help.

**E11 · Portuguese (Brazil)**
- `_locales/en/messages.json` and `_locales/pt_BR/messages.json`, with `default_locale: "en"`.
- A `t(key, ...subs)` helper (extension/lib/i18n.js) loads both files and picks one by storage.local `lang`. `auto` means Portuguese when the browser language starts with "pt"; the other values are `en` and `pt_BR`. Settings → Language sets it.
- panel.html uses `data-i18n`, `data-i18n-title`, `data-i18n-placeholder` and `data-i18n-aria-label`; panel.js and background.js use t().
- The helper's confirm windows get the language in hello (`lang`) and carry both texts.
- Tests check that every key exists in both files, and that panel.html has no visible text without a data-i18n attribute (with an allowlist for brand names and symbols).

**E12 · fill_form**
- `fill_form {fields: [{ref | selector, value}]}`, up to 30 fields.
- The page operation resolves each field's label and refuses sensitive fields before anything is shown.
- The card lists label → value (values cut to 80 characters), with Approve and Deny. Approve fills each field the way fill does and reports per field.
- It never submits, and it isn't offered to workers.

**E13 · Uploads and dialogs**
- `upload_file {ref | selector, path}`:
  - the file must pass guard.readable, sit inside a granted local-page folder or the file-tools folder, and be at most 25 MB;
  - its card always shows, even in Trusted mode: "Claude wants to upload `<name>` (`<size>`) to `<site>`";
  - the page operation attaches it with DataTransfer and fires input and change.
- Dialogs: during a click, Enter or submit by Claude (and for 1 s after), the page operation replaces alert, confirm and prompt in the page.
  - alert is dismissed;
  - confirm returns `accept_dialog === true`;
  - prompt returns null, or `dialog_text` when accepted.
  The tool result adds: `The page showed a <kind>: "<text>" (answered OK|Cancel).`

**E14 · Accessibility**
- Command `stop-claude`, with suggested key Alt+Shift+X, runs Stop.
- The input keeps focus after sending.
- The progress list is aria-live polite.

## U. UX

**U2 · Two accounts**
- When the claude.ai email and the Claude Code email differ, a chat's first message shows a card: "This browser is signed in to claude.ai as `<A>`, but chats run on Claude Code as `<B>`." The buttons: Use `<B>` for this chat, or Open Accounts. The choice lasts for the chat.

**U4 · Queue, cap, log**
- While Claude answers, sending queues the message, shown as a pending bubble with ×. Queued messages go out in order when the answer ends. One answer runs at a time across all windows.
- While an answer runs, the hint under the input says `Claude is answering · stops after 1 hour`.
